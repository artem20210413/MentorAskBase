# Feature Specification: Підтримка Word та текстових документів

**Feature Branch**: `002-word-txt-documents`

**Created**: 2026-09-12

**Status**: Draft

## Clarifications

### Session 2026-09-12

- Q: Для PDF без розпізнаваного тексту система робить OCR через vision-модель (PdfVisionExtractor). Чи потрібна аналогічна OCR-обробка для .docx з зображеннями замість тексту? → A: Так, якщо .docx містить зображення, їх вміст має бути розпізнаний через OCR (vision-модель), так само як для сканованих PDF.
- Q: Яке кодування .txt-файлів система має гарантовано підтримувати (окрім UTF-8)? → A: Тільки UTF-8; файли в інших кодуваннях позначаються як необроблені з поясненням причини.
- Q: Для фрагментів з .docx/.txt (де немає поняття "сторінка") — як заповнювати page_number? → A: Залишати порожнім/null.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Завантаження документа Word (Priority: P1)

Адміністратор бази знань завантажує файл у форматі Word (.docx), щоб його вміст став джерелом для відповідей бота, так само як зараз працює з PDF.

**Why this priority**: Word — один із двох нових форматів, явно запитаних користувачем, і найпоширеніший формат текстових документів у офісному середовищі.

**Independent Test**: Завантажити коректний .docx-файл через існуючий інтерфейс завантаження; переконатися, що документ отримує статус "оброблено", а його текст розбитий на фрагменти та доступний для пошуку.

**Acceptance Scenarios**:

1. **Given** адміністратор має коректний файл `document.docx`, **When** він завантажує його, **Then** система приймає файл, ставить у чергу обробки і зрештою позначає статус "оброблено".
2. **Given** документ .docx успішно оброблено, **When** користувач у чаті ставить питання, відповідь на яке міститься в цьому документі, **Then** бот використовує фрагменти з цього документа для формування відповіді.
3. **Given** файл має розширення `.docx`, але пошкоджений або не є валідним Word-документом, **When** адміністратор намагається його завантажити, **Then** система відхиляє завантаження з повідомленням про помилку валідації (аналогічно до пошкоджених PDF).

---

### User Story 2 - Завантаження текстового файлу (Priority: P2)

Адміністратор бази знань завантажує звичайний текстовий файл (.txt) з готовим текстом, щоб додати його як джерело знань без конвертації в PDF чи Word.

**Why this priority**: .txt — другий явно запитаний формат; має нижчий пріоритет за Word, оскільки простіший у реалізації (немає складного парсингу структури) і рідше використовується для великих документів.

**Independent Test**: Завантажити файл `notes.txt` з текстом у кодуванні UTF-8; переконатися, що документ обробляється і фрагменти з нього беруть участь у пошуку відповідей.

**Acceptance Scenarios**:

1. **Given** адміністратор має файл `notes.txt` у кодуванні UTF-8, **When** він завантажує його, **Then** система приймає файл, обробляє його текст і позначає статус "оброблено".
2. **Given** текстовий файл успішно оброблено, **When** користувач ставить питання, відповідь на яке міститься в цьому файлі, **Then** бот використовує фрагменти з цього файлу у відповіді.

---

### User Story 3 - Уніфікована поведінка незалежно від формату (Priority: P3)

Адміністратор бачить та керує документами Word, .txt і PDF однаково — в одному списку, з однаковими діями (перегляд статусу, видалення, дедуплікація), без потреби розрізняти формати вручну.

**Why this priority**: Забезпечує узгодженість продукту й уникнення дублювання інтерфейсу/логіки, але не є критичним для того, щоб нові формати вже приносили користь.

**Independent Test**: Завантажити по одному файлу кожного підтримуваного формату (PDF, .docx, .txt) і переконатися, що всі вони відображаються в єдиному списку документів з однаковими можливими діями та однаковою логікою дедуплікації за вмістом.

**Acceptance Scenarios**:

1. **Given** у системі є документи різних форматів, **When** адміністратор відкриває список документів, **Then** усі документи (PDF, Word, текстові) показані в одному списку з однаковим набором полів (назва, статус, дата).
2. **Given** уже завантажено .docx-файл з певним вмістом, **When** хтось повторно завантажує файл з ідентичним вмістом (навіть іншою назвою), **Then** система позначає новий запис як дублікат так само, як це відбувається зараз для PDF.
3. **Given** документ Word або текстовий файл видалено (м'яко), **When** відбувається пошук відповіді на запит користувача, **Then** фрагменти видаленого документа не беруть участі в пошуку — так само, як для PDF.

---

### Edge Cases

- Що відбувається, якщо .docx-файл містить зображення (наприклад, скановану сторінку, вставлену як картинку) замість чи на додачу до тексту? Система розпізнає вміст зображень через OCR (vision-модель), так само як зараз для сканованих PDF, і додає розпізнаний текст до вмісту документа.
- Що відбувається, якщо .docx-файл не містить жодного розпізнаваного вмісту навіть після OCR зображень (порожній вміст після вилучення)? Система має позначити документ як такий, що не вдалось обробити, з поясненням причини — так само, як зараз для PDF без тексту.
- Як система реагує на файл з розширенням `.docx`, який насправді не є валідним Word-документом (підміна розширення)? Відхилити при синхронній перевірці формату, не ставлячи в чергу обробки.
- Як система реагує на `.txt`-файл у кодуванні, відмінному від UTF-8 (наприклад, Windows-1251)? Система позначає документ як необроблений з поясненням причини — гарантована підтримка обмежена UTF-8.
- Що відбувається з дуже великим текстовим/Word-файлом, що перевищує загальний ліміт розміру завантаження? Відхиляється так само, як зараз перевищення ліміту для PDF.
- Що відбувається, якщо .docx-файл захищений паролем? Позначається як необроблений з поясненням причини (аналогічно нечитабельному PDF).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST приймати для завантаження файли у форматі Word (`.docx`) на додачу до вже підтримуваного PDF.
- **FR-002**: Система MUST приймати для завантаження звичайні текстові файли (`.txt`) на додачу до вже підтримуваного PDF.
- **FR-003**: Система MUST синхронно перевіряти цілісність і відповідність формату файлу під час завантаження для .docx та .txt, відхиляючи пошкоджені або невалідні файли з поясненням причини — так само, як зараз для PDF.
- **FR-004**: Система MUST вилучати текстовий вміст з .docx та .txt файлів і розбивати його на фрагменти для пошуку тим самим способом (та за тими самими правилами релевантності), що й для PDF.
- **FR-004a**: Система MUST розпізнавати текст із зображень, вбудованих у .docx-файл, за допомогою OCR (vision-моделі), і включати розпізнаний текст у вміст документа — так само, як зараз відбувається для сканованих PDF.
- **FR-004b**: Система MUST обмежувати гарантовану підтримку кодування .txt-файлів лише UTF-8; файли в інших кодуваннях система MUST позначати як необроблені з поясненням причини, а не намагатися автоматично перекодувати.
- **FR-005**: Система MUST застосовувати той самий ліміт максимального розміру файлу до .docx та .txt, що й до PDF.
- **FR-006**: Система MUST дедуплікувати .docx та .txt документи за вмістом файлу так само, як зараз відбувається для PDF.
- **FR-007**: Система MUST відображати документи Word і текстові документи в єдиному списку документів разом з PDF, з однаковим набором відображуваних полів (назва, статус обробки, дата завантаження, причина помилки).
- **FR-008**: Система MUST застосовувати ті самі дії керування (м'яке видалення, остаточне видалення після періоду очікування) до документів Word і текстових документів, що й до PDF.
- **FR-009**: Система MUST виключати фрагменти м'яко видалених Word- та текстових документів з пошуку відповідей — так само, як для PDF.
- **FR-010**: Система MUST позначати документ статусом, що описує невдалу обробку (з причиною), якщо з .docx- або .txt-файлу не вдалося вилучити придатний для пошуку текст.

### Key Entities

- **Документ (Document)**: вже існуюча сутність; розширюється підтримкою нових вихідних форматів файлу (Word, текстовий) на додачу до PDF. Формат вихідного файлу не є окремим полем, видимим користувачу, — документи всіх форматів рівноправні в списку.
- **Фрагмент документа (DocumentChunk)**: вже існуюча сутність; для .txt та .docx поле номера сторінки залишається порожнім (null), оскільки ці формати не мають чіткої концепції "сторінки"; позиція фрагмента в документі заповнюється так само, як для PDF.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Адміністратор може завантажити коректний .docx-файл і отримати статус "оброблено" без додаткових ручних дій, так само просто, як зараз для PDF.
- **SC-002**: Адміністратор може завантажити коректний .txt-файл і отримати статус "оброблено" без додаткових ручних дій.
- **SC-003**: 100% питань користувачів, відповідь на які міститься виключно у завантаженому Word- або текстовому документі, отримують відповідь з посиланням на вміст цього документа (за тих самих умов релевантності, що застосовуються до PDF).
- **SC-004**: Пошкоджені або невалідні файли .docx та .txt відхиляються під час завантаження в 100% випадків, без потрапляння в чергу обробки.
- **SC-005**: Список документів показує документи всіх трьох форматів (PDF, Word, текстовий) без відмінностей у структурі відображення.

## Assumptions

- Підтримка Word обмежується сучасним форматом `.docx` (Office Open XML); застарілий бінарний формат `.doc` — поза межами цієї функції.
- Текстові файли передбачаються у звичайному форматі `.txt`; форматований/розмічений текст (Markdown, RTF тощо) — поза межами цієї функції.
- Гарантовано підтримується лише кодування UTF-8 для текстових файлів; файли в інших кодуваннях позначаються як необроблені, а не автоматично перекодовуються.
- Ліміт розміру файлу (наразі 50 МБ) залишається спільним для всіх форматів, а не задається окремо для кожного.
- Логіка дедуплікації, м'якого видалення та остаточного видалення, що вже існує для PDF, переноситься на нові формати без змін у поведінці.
- Концепція "сторінки" для .txt та .docx не застосовна; номер сторінки у фрагментах цих форматів залишається порожнім (null), без впливу на якість пошуку.
