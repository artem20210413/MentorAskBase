# Phase 0 Research: Підтримка Word та текстових документів

## 1. Вилучення тексту та зображень з `.docx`

**Decision**: `phpoffice/phpword` (пакет Composer) для читання `.docx` —
ітерація по секціях/елементах документа для тексту та по вбудованих медіа
(`Element\Image`) для зображень.

**Rationale**: `.docx` — це ZIP-контейнер з XML (Office Open XML). Ручний
парсинг XML/ZIP дублював би функціональність, яку `phpoffice/phpword`
надає готовою (обхід параграфів, таблиць, вбудованих зображень) і яка вже є
де-факто стандартом для PHP-екосистеми (аналогічно до того, як
`smalot/pdfparser` уже використовується для PDF). Це узгоджується з
Принципом III конституції (Simplicity) — не винаходити читач docx з нуля.

**Alternatives considered**:
- Ручний unzip + `SimpleXMLElement` над `word/document.xml` — відхилено:
  довелось би самостійно реалізувати обробку стилів/таблиць/посилань на
  зображення, що `phpoffice/phpword` уже інкапсулює.
- `libreoffice --headless --convert-to txt` (shell-виклик) — відхилено:
  зовнішня системна залежність поза Composer, ускладнює розгортання
  (Технологічні обмеження конституції — уникати нових інструментів збірки
  без потреби).

## 2. OCR зображень, вбудованих у `.docx`

**Decision**: Перевикористати наявну vision-модель (той самий OpenAI
vision-виклик, що й `PdfVisionExtractor`), винісши спільну логіку
"зображення → транскрибований текст" у окремий перевикористовуваний сервіс
(`VisionTranscriber`), яким користуються і `PdfVisionExtractor` (сторінки
PDF як зображення), і новий екстрактор `.docx` (вбудовані зображення).

**Rationale**: Уточнення (сесія 2026-09-12) вимагає OCR для зображень у
`.docx`. Промпт і механізм ретраю (`OpenAiRetry`) для транскрибування
зображення в текст вже існують і не залежать від того, звідки взялося
зображення (сторінка PDF чи вбудований малюнок docx) — виділення спільного
сервісу уникає дублювання коду (Принцип III).

**Alternatives considered**:
- Окремий OCR-рушій (Tesseract) лише для docx-зображень — відхилено:
  два різні механізми розпізнавання зображень для одного продукту
  ускладнюють підтримку якості й консистентності без явної потреби.

## 3. Читання `.txt`

**Decision**: Пряме читання вмісту файлу (`file_get_contents`) з перевіркою
кодування через `mb_check_encoding($content, 'UTF-8')`. Якщо перевірка не
проходить — документ позначається `failed` із причиною "непідтримуване
кодування".

**Rationale**: Уточнення зафіксувало, що гарантується лише UTF-8; жодних
додаткових бібліотек для визначення/перекодування кодувань не потрібно —
найпростіше рішення, що покриває вимогу (Принцип III).

**Alternatives considered**:
- `mb_detect_encoding` + автоматичне перекодування в UTF-8 — відхилено
  уточненням користувача (гарантія лише UTF-8, без спроб автовизначення).

## 4. Валідація формату при завантаженні (FR-003)

**Decision**: Розширити правило валідації `UploadDocumentRequest` з
`mimes:pdf` на `mimes:pdf,docx,txt`, і додатково для `.docx` — синхронна
перевірка через спробу відкрити файл `phpoffice/phpword` (аналогічно
`PdfTextExtractor::assertReadable()` для PDF), для `.txt` — перевірка
`mb_check_encoding`.

**Rationale**: Laravel-правило `mimes` вже покриває базову перевірку
розширення/MIME на рівні HTTP-запиту (FR-001b — та сама схема, що й для
PDF); глибша перевірка цілісності (файл дійсно є валідним docx, а не
підміненим розширенням) виконується в сервісному шарі так само, як зараз
для PDF через `assertReadable()`.

**Alternatives considered**: немає — пряме розширення наявного,
перевіреного підходу.

## 5. Визначення типу джерела документа в конвеєрі обробки

**Decision**: Тип файлу (pdf/docx/txt) визначається за розширенням
`original_name` (уже зберігається на моделі `Document`) у момент обробки
(`ProcessDocumentJob`) — без додавання нового стовпця в БД.

**Rationale**: Розширення файлу вже валідується при завантаженні (FR-003),
тому воно є надійним джерелом істини для вибору екстрактора; додавання
окремого стовпця "тип документа" було б надлишковою абстракцією для
атрибута, що й так однозначно виводиться з наявних даних (Принцип III).

**Alternatives considered**:
- Новий стовпець `documents.source_type` — відхилено як передчасну
  абстракцію: наразі немає вимоги фільтрувати/відображати документи за
  типом файлу (FR-007 вимагає єдиного списку без розрізнення форматів).

## 6. Значення `source` для фрагментів `.docx`/`.txt`

**Decision**: Перевикористати наявний enum `document_chunks.source`
(`text_layer`, `vision_ocr`) без міграції: текст, вилучений напряму з
`.docx`/`.txt`, отримує `text_layer`; текст, розпізнаний OCR із вбудованого
зображення `.docx`, отримує `vision_ocr` — та сама семантика, що й для PDF.

**Rationale**: Існуючі значення enum вже точно описують походження тексту
незалежно від формату файлу-джерела; нових станів не потрібно.

**Alternatives considered**: додавання нових значень enum (`docx_text`,
`txt_raw`) — відхилено як надлишкове дроблення без функціональної різниці.
