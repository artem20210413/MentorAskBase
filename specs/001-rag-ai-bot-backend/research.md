# Phase 0 Research: RAG AI Bot Backend (API MVP)

Усі пункти "NEEDS CLARIFICATION" з Technical Context вирішено нижче.

## 1. Векторне сховище

**Decision**: PostgreSQL 16 + розширення `pgvector`, колонка `vector` у
таблиці `document_chunks`, індекс `HNSW` (або `IVFFlat` як запасний варіант)
для пошуку найближчих сусідів.

**Rationale**:
- Один storage замість двох — документи, чанки, сесії розмов і журнал живуть
  в одній БД; менше інфраструктури для підняття через Sail.
- Eloquent-сумісність: ембединги — звичайна колонка, стандартні міграції.
- LLPhant з коробки підтримує PostgreSQL/pgvector як vector store.
- Відповідає SC-008 (до ~1000 документів, 5-10 одночасних користувачів) —
  pgvector впевнено тримає цей масштаб без спеціалізованого векторного
  сервера.
- Відповідає Принципу III конституції (Simplicity/YAGNI).

**Alternatives considered**:
- **Qdrant (REST API)** — потужніший для мільйонів векторів і гібридного
  пошуку, але додає окремий сервіс, окремий HTTP-клієнт і точку відмови;
  невиправдана складність для поточного масштабу. Залишається кандидатом,
  якщо база знань виросте на порядки.
- **Elasticsearch/OpenSearch з vector search** — надлишково важкий для MVP,
  типово використовується коли вже є текстовий повнотекстовий пошук поруч.

## 2. LLM-провайдер (чат-модель для відповідей)

**Decision**: Конфігурований провайдер через `openai-php/laravel` як основний
клієнт; за замовчуванням — OpenAI `gpt-4o-mini` (баланс якості/вартості для
RAG-відповідей). Google Gemini залишається альтернативою через окремий
конфігураційний драйвер (адаптер), що обирається змінною середовища.

**Rationale**:
- Користувач прямо просив пропозицію моделі; `gpt-4o-mini` — стандартний
  вибір для RAG-задач такого масштабу: дешевший за `gpt-4o`, достатньо
  якісний для відповідей на основі наданого контексту (a не creative writing).
- LLPhant з коробки має адаптери як для OpenAI, так і для інших провайдерів —
  архітектура не прив'язується жорстко до одного постачальника (відповідає
  припущенню в spec.md про те, що вибір провайдера — рішення рівня плану, а
  не жорстка вимога).
- `openai-php/laravel` — офіційно підтримуваний пакет, добре документований,
  проста інтеграція з Laravel Service Container і конфігурацією.

**Alternatives considered**:
- **Google Gemini напряму (`google-gemini-php/laravel` або HTTP-клієнт)** —
  розглядається як рівноцінна альтернатива за вартістю; не обрано за
  замовчуванням лише через ширшу екосистему готових Laravel-інтеграцій у
  OpenAI на момент розробки. Архітектура (адаптер у `AnswerGenerationService`)
  дозволяє додати як другий драйвер без переробки.
- **Anthropic Claude API напряму** — не згадувався користувачем, не обрано за
  замовчуванням, але сумісний з тим самим адаптерним підходом за потреби.

## 3. Розпізнавання зображень/сканованих сторінок (vision-модель)

**Decision**: `gpt-4o-mini` (той самий провайдер, мультимодальний режим) для
розпізнавання сторінок PDF без текстового шару: сторінка рендериться в
зображення (`spatie/pdf-to-image` + `imagick`), надсилається у vision-запит,
розпізнаний текст додається до пайплайну чанкінгу нарівні зі звичайним
текстовим шаром.

**Rationale**:
- Той самий провайдер/SDK, що й для чат-відповідей — не потрібен другий
  контракт інтеграції чи окремий API-ключ.
- `gpt-4o-mini` підтримує vision-вхід і суттєво дешевший за спеціалізовані
  OCR-хмарні сервіси при цьому обсязі документів (до ~1000).

**Alternatives considered**:
- **Google Cloud Vision / AWS Textract (спеціалізований OCR)** — точніший для
  складних сканів (таблиці, рукописний текст), але додає третього зовнішнього
  постачальника й окремий контракт інтеграції; надлишково для MVP.
- **Tesseract OCR (локально, безкоштовно)** — усуває залежність від
  зовнішнього API, але помітно гірша якість на складних макетах і
  розгорнутих зображеннях; не розпізнає контекст (діаграми, графіки) так, як
  vision LLM. Залишається кандидатом для здешевлення в майбутньому як
  перший прохід перед fallback на vision-модель.

## 4. RAG-оркестрація

**Decision**: `theodo-group/llphant` як шар оркестрації: chunking, виклик
embeddings API, запис/пошук у векторному сховищі, збірка промпту з
retrieved-контекстом.

**Rationale**:
- Головний PHP-аналог LangChain — вже запропонований користувачем, добре
  задокументований, підтримує PostgreSQL/pgvector з коробки.
- Знімає потребу писати власний RAG-пайплайн (chunking-стратегії, promt
  templates) з нуля — відповідає Принципу III (Simplicity).

**Alternatives considered**:
- **Власна реалізація RAG-пайплайну** (лише `openai-php/laravel` +
  ручний SQL для pgvector) — більше контролю, але значно більше коду для
  підтримки на старті проєкту; відхилено на користь готового фреймворку.

## 5. Автентифікація технічним токеном (FR-013)

**Decision**: Laravel Sanctum, персональні токени доступу (`personal access
tokens`) без прив'язки до повноцінної моделі User із паролем — технічний
токен видається вручну (seeder/artisan-команда) на цьому етапі.

**Rationale**:
- Sanctum вже є частиною стандартної Laravel-екосистеми, легко інтегрується
  з `throttle` middleware для rate limiting (FR-013a/b).
- Дає прямий шлях міграції до повної системи користувачів/авторизації
  пізніше (Sanctum підтримує обидва режими) — відповідає FR-014 (архітектура
  готова до майбутніх каналів) без надлишкової складності зараз.

**Alternatives considered**:
- **Кастомний статичний API-ключ у `.env`** — простіше, але не дає
  стандартного шляху до rate limiting per-token і ускладнює міграцію до
  Sanctum-токенів пізніше; відхилено.

## 6. Rate limiting (FR-013a/b)

**Decision**: Вбудований Laravel `throttle` middleware, прив'язаний до
ідентифікатора Sanctum-токена (а не IP), з конфігурованим лімітом
(`RATE_LIMIT_PER_MINUTE` у `.env`), що повертає стандартну `429 Too Many
Requests` відповідь з заголовком `Retry-After`.

**Rationale**: Нативне рішення Laravel, жодних додаткових залежностей;
`Retry-After` — стандартний спосіб повідомити час очікування (узгоджено в
Clarifications spec.md).

## 7. Визначення мови питання (FR-009a/b)

**Decision**: Легка бібліотека визначення мови (`patrickschur/language-detection`,
не потребує зовнішнього API) для швидкого визначення мови тексту питання;
перелік підтримуваних мов і мова за замовчуванням — конфігурація
(`config/rag.php` → `supported_languages`).

**Rationale**: Не залежить від додаткового виклику LLM (економія часу й
вартості); достатньо точний для коротких питань природною мовою.

**Alternatives considered**:
- **Просити LLM саму визначити й відповісти відповідною мовою через
  системний промпт** — простіше в реалізації (без нової залежності), але
  менш детерміновано і не дає системі точки контролю для FR-009b
  (примусова відповідь мовою за замовчуванням, якщо мова непідтримувана).
  Може бути прийнято як спрощення на етапі `/speckit-tasks`, якщо швидкість
  розробки важливіша за детермінізм.

## 8. Асинхронна обробка документів

**Decision**: Стандартна Laravel Queue (`database` driver в межах Sail;
легко перемкнути на `redis`), одна job `ProcessDocumentJob` на документ,
що виконує: текстову екстракцію → (за потреби) vision-розпізнавання →
чанкінг → ембединг → запис у БД, з оновленням статусу документа на кожному
кроці (FR-007).

**Rationale**: Немає потреби у Redis/окремому брокері на цьому масштабі
(SC-008); `database` driver достатній і не додає інфраструктури понад
PostgreSQL, яка вже потрібна для pgvector.

## Підсумок

Усі технічні невизначеності Technical Context вирішено. Жодних відкритих
`NEEDS CLARIFICATION` не залишилось для переходу до Phase 1.
