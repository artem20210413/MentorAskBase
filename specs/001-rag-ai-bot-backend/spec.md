## Clarifications

### Session 2026-09-06

- Q: Який максимальний розмір файлу дозволено завантажувати до бази знань? → A: 50 МБ
- Q: Що робити, якщо два запити на завантаження файлу з однаковим хешем надходять одночасно (до завершення обробки першого)? → A: Другий запит очікує результат першого (не запускає повторну обробку і не створює дублікат)
- Q: Який очікуваний масштаб для MVP (кількість документів у базі знань і одночасних запитів)? → A: До ~1000 документів у базі знань, кілька одночасних користувачів (5-10)
- Q: Чи потрібне обмеження частоти запитів (rate limiting) для технічного токена доступу до API на цьому етапі? → A: Так, базовий ліміт на кількість запитів за проміжок часу на токен
- Q: Що робити, якщо клієнт надсилає питання з ідентифікатором сесії, якої не існує (наприклад, вигаданий або вже видалений id)? → A: Автоматично створювати нову сесію з новим ідентифікатором
- Q: Файл пошкоджений або має непідтримуваний формат — коли система це виявляє? → A: Одразу при завантаженні, синхронна відмова
- Q: Оператор намагається видалити документ, фрагменти якого саме зараз використовуються для формування відповіді на активний запит. Що робити? → A: Дозволити видалення негайно
- Q: Зовнішній сервіс LLM тимчасово недоступний або повертає помилку під час формування відповіді на питання. Що робити? → A: Одна автоматична повторна спроба, потім помилка клієнту
- Q: Коли клієнт перевищує базовий ліміт частоти запитів (rate limit) для свого токена, як має реагувати система? → A: Відхиляти запит із чіткою помилкою і часом очікування до наступної спроби

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Завантаження документа у базу знань (Priority: P1)

Оператор (тестувальник API на цьому етапі) завантажує файл документа (наприклад,
PDF), і система обробляє його: розбиває на фрагменти, перетворює на векторні
представлення (ембединги) і зберігає так, щоб надалі система могла знаходити
релевантні фрагменти для відповідей на питання.

**Why this priority**: Без завантаженої та проіндексованої бази знань система
не має що використати для відповідей — це фундамент усієї RAG-функціональності.

**Independent Test**: Можна перевірити незалежно, надіславши файл через API
ендпоінт завантаження і переконавшись, що документ позначений як оброблений
(проіндексований) і доступний для пошуку.

**Acceptance Scenarios**:

1. **Given** новий файл документа ще не завантажувався раніше, **When**
   оператор надсилає його через API завантаження, **Then** система приймає
   файл, обробляє його асинхронно і позначає як готовий до використання в
   відповідях.
2. **Given** файл містить переважно зображення/скановані сторінки (типово для
   деяких PDF), **When** система обробляє його, **Then** зміст із зображень
   MUST бути розпізнаний і включений у базу знань (а не пропущений мовчки).
3. **Given** файл із таким самим вмістом (той самий хеш) вже було завантажено
   і проіндексовано раніше, **When** оператор завантажує його повторно,
   **Then** система розпізнає дублікат і НЕ виконує повторну векторизацію,
   а використовує вже наявний результат.

---

### User Story 2 - Отримання відповіді на питання через API (Priority: P1)

Клієнт API надсилає текстове питання. Система знаходить найбільш релевантні
фрагменти з раніше завантажених документів, формує запит до мовної моделі
(LLM) і повертає відповідь, засновану на цих фрагментах.

**Why this priority**: Це основна цінність продукту — відповідь на питання на
основі власної бази знань, а не лише загальних знань моделі.

**Independent Test**: Можна перевірити незалежно, надіславши питання про факт,
який присутній лише в завантаженому документі, і переконавшись, що відповідь
містить правильну інформацію з цього документа.

**Acceptance Scenarios**:

1. **Given** база знань містить проіндексований документ з певним фактом,
   **When** клієнт надсилає питання про цей факт, **Then** система повертає
   відповідь, що коректно відображає цей факт.
2. **Given** питання не стосується жодного з завантажених документів, **When**
   клієнт надсилає таке питання, **Then** система повертає відповідь, яка
   чесно повідомляє про відсутність релевантної інформації в базі знань, а не
   вигадану відповідь.
3. **Given** кожен запит питання-відповідь, **When** система обробляє його,
   **Then** питання, відповідь та метадані (час, сесія) MUST бути записані в
   журнал (лог) для подальшого аналізу.

---

### User Story 3 - Продовження розмови з пам'яттю контексту (Priority: P2)

Клієнт API веде послідовність питань у межах однієї розмови (сесії). Система
пам'ятає попередні питання й відповіді в межах цієї сесії та враховує їх при
формуванні наступної відповіді.

**Why this priority**: Без пам'яті розмови кожне питання ізольоване, що не
дозволяє вести природний діалог (наприклад, уточнювальні питання на кшталт
«а що щодо...»). Це друга за важливістю можливість після базового RAG-запиту.

**Independent Test**: Можна перевірити незалежно, надіславши послідовність із
двох пов'язаних питань в межах однієї сесії (друге посилається на контекст
першого без повторення деталей) і переконавшись, що друга відповідь коректно
враховує контекст першого обміну.

**Acceptance Scenarios**:

1. **Given** клієнт розпочав нову розмову, **When** він надсилає перше
   питання, **Then** система створює нову сесію розмови й повертає відповідь
   разом з ідентифікатором цієї сесії.
2. **Given** існуюча сесія з попередніми питаннями й відповідями, **When**
   клієнт надсилає наступне питання в межах тієї самої сесії, **Then**
   система враховує попередній контекст розмови при формуванні відповіді.
3. **Given** сесія розмови, **When** минає час без нових повідомлень, що
   перевищує налаштований тайм-аут неактивності (типово 1 година; значення
   налаштовується, а вимкнення тайм-аута — тобто безстрокове зберігання
   контексту — MUST бути можливим окремим налаштуванням), **Then** система
   вважає сесію завершеною: наступне повідомлення з тим самим ідентифікатором
   починає розмову без попереднього контексту.

---

### User Story 4 - Веб-інтерфейс керування документами бази знань (Priority: P2)

Оператор відкриває просту веб-сторінку (без входу в систему на цьому етапі),
бачить список уже завантажених документів із їхнім статусом обробки, може
завантажити новий файл через форму на сторінці та видалити непотрібний
документ (м'яке видалення — документ і його фрагменти/вектори перестають
використовуватися, але не стираються фізично одразу, див. FR-017a).

**Why this priority**: Керування базою знань лише через прямі API-виклики
незручне для щоденної роботи оператора; проста веб-морда прискорює наповнення
й підтримку бази знань у актуальному стані, але не є критичною для базової
роботи RAG-відповідей (тому P2, а не P1).

**Independent Test**: Можна перевірити незалежно, відкривши сторінку в
браузері, завантаживши файл через форму та переконавшись, що він з'явився у
списку зі статусом обробки, а потім видаливши документ зі списку і
переконавшись, що він і його фрагменти більше не використовуються для
відповідей.

**Acceptance Scenarios**:

1. **Given** оператор відкрив сторінку керування документами, **When**
   сторінка завантажується, **Then** він бачить перелік усіх завантажених
   документів з назвою, статусом обробки та датою завантаження.
2. **Given** оператор на сторінці керування документами, **When** він обирає
   файл через форму завантаження і підтверджує, **Then** файл завантажується
   так само, як через API (FR-001–FR-007), і з'являється у списку зі
   статусом «в черзі»/«обробляється».
3. **Given** список документів містить раніше завантажений документ, **When**
   оператор натискає «видалити» і підтверджує дію, **Then** система позначає
   документ і його фрагменти/векторні представлення як видалені (м'яке
   видалення, FR-017a), і він більше не використовується для формування
   відповідей та не відображається в списку.
4. **Given** сторінка керування документами відкрита без будь-якого входу в
   систему (авторизація на цьому етапі відсутня), **When** будь-хто з
   доступом до мережі, де розгорнутий застосунок, відкриває цю сторінку,
   **Then** він отримує повний доступ до перегляду, завантаження та
   видалення документів (це прийнятний тимчасовий компроміс до впровадження
   авторизації).

---

### User Story 5 - Прозорість джерел відповіді (Priority: P2)

Разом з текстом відповіді клієнт отримує перелік документів (і за потреби —
конкретних фрагментів), на основі яких сформовано цю відповідь, щоб мати
змогу перевірити достовірність і за потреби звернутися до першоджерела.

**Why this priority**: Без видимих джерел відповідь LLM — це «чорна скринька»,
якій важко довіряти й яку неможливо верифікувати; для бази знань це особливо
критично. Не є P1, бо базова RAG-відповідь (User Story 2) працює й без цього.

**Independent Test**: Можна перевірити незалежно, поставивши питання, чия
відповідь спирається на конкретний документ, і переконавшись, що у відповіді
API присутнє посилання саме на цей документ.

**Acceptance Scenarios**:

1. **Given** відповідь сформована на основі одного чи кількох фрагментів бази
   знань, **When** клієнт отримує відповідь, **Then** разом з текстом
   відповіді MUST передаватися перелік документів-джерел (щонайменше назва
   документа), використаних для формування цієї відповіді.
2. **Given** система не знайшла релевантної інформації (FR-009), **When**
   вона повертає відповідь про відсутність інформації, **Then** перелік
   джерел MUST бути порожнім (немає сенсу показувати нерелевантні джерела).

---

### User Story 6 - Зворотний зв'язок щодо якості відповіді (Priority: P3)

Клієнт може позначити конкретну відповідь як корисну чи некорисну (і за
бажання додати короткий коментар), щоб цю оцінку можна було використати для
подальшого аналізу якості бота.

**Why this priority**: Корисна для довгострокового покращення якості, але не
впливає на роботу базового RAG-функціоналу — найнижчий пріоритет з нових
можливостей.

**Independent Test**: Можна перевірити незалежно, надіславши оцінку до вже
отриманої відповіді (за її ідентифікатором у журналі) і переконавшись, що
оцінка збережена та пов'язана саме з цим записом питання-відповідь.

**Acceptance Scenarios**:

1. **Given** клієнт отримав відповідь на питання, **When** він надсилає
   оцінку («корисно» / «некорисно») для цієї відповіді, **Then** система
   MUST зберегти оцінку, пов'язану з відповідним записом журналу
   питання-відповідь.
2. **Given** клієнт додає текстовий коментар разом з оцінкою, **When** оцінка
   зберігається, **Then** коментар MUST зберігатися разом з оцінкою.
3. **Given** запис журналу, для якого оцінку вже залишено, **When** клієнт
   надсилає нову оцінку для того самого запису, **Then** система MUST
   замінити попередню оцінку новою (не накопичувати дублікати).

---

### Edge Cases

- Що відбувається, якщо файл дуже великий (у межах ліміту 50 МБ) і обробка
  (векторизація) триває довго — чи отримує клієнт статус прогресу? (див.
  статуси обробки в FR-007)
- Що відбувається при спробі видалити документ, якого вже не існує (наприклад,
  видалений раніше в іншій вкладці)? Система MUST повертати чітку помилку
  «документ не знайдено», не викликаючи збою сторінки.
- Як система реагує, якщо питання написане мовою, що не входить до переліку
  підтримуваних мов? (див. FR-009b — відповідь мовою за замовчуванням)
- Як система реагує, якщо в межах однієї сесії розмови користувач змінює мову
  питання (наприклад, перше питання українською, друге — англійською)? Мова
  визначається окремо для кожного питання (див. FR-009a), тож відповідь на
  друге питання буде англійською, попри те, що сесія та ж сама.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST надавати API-ендпоінт для завантаження файлу
  документа (щонайменше формат PDF) до бази знань.
- **FR-001a**: Система MUST відхиляти файли, розмір яких перевищує 50 МБ,
  з чітким повідомленням про причину відмови, і не створювати для них запис
  документа.
- **FR-001b**: Система MUST перевіряти формат і цілісність файлу одразу під
  час запиту завантаження (синхронно) і відхиляти запит з чіткою причиною
  відмови, якщо файл пошкоджений або має непідтримуваний формат; такий файл
  MUST не створювати запис документа і не потрапляти в чергу асинхронної
  обробки.
- **FR-002**: Система MUST обчислювати хеш вмісту кожного завантаженого файлу
  й перевіряти його на збіг із раніше завантаженими файлами перед обробкою.
- **FR-003**: Система MUST пропускати повторну векторизацію (ембединг) для
  файлу, чий хеш вже збігається з раніше обробленим файлом.
- **FR-003a**: Якщо запит на завантаження файлу з хешем, що вже перебуває в
  обробці (обробка ще не завершена), надходить повторно, система MUST не
  запускати паралельну повторну обробку, а повʼязати новий запит з
  результатом вже наявної обробки (другий запит очікує на завершення першої
  обробки того самого файлу).
- **FR-004**: Система MUST розбивати вміст нового документа на фрагменти
  (чанки) і перетворювати кожен фрагмент на векторне представлення для
  подальшого пошуку.
- **FR-005**: Система MUST розпізнавати текстовий вміст із зображень/сторінок
  документа, коли текстовий шар відсутній або недостатній (наприклад,
  скановані сторінки PDF), і включати розпізнаний текст в індексацію.
- **FR-006**: Обробка завантаженого документа (розбиття, розпізнавання,
  векторизація) MUST виконуватися асинхронно, не блокуючи відповідь на запит
  завантаження.
- **FR-007**: Система MUST надавати спосіб дізнатися статус обробки
  завантаженого документа. Документ MUST перебувати рівно в одному з таких
  статусів у кожен момент часу:
  - **Очікує обробки** — файл прийнято й збережено, обробка ще не почалася
    (в черзі).
  - **Обробляється** — триває розбиття на фрагменти, розпізнавання
    зображень (за потреби) та/або векторизація.
  - **Оброблено** — документ повністю проіндексований і його фрагменти
    використовуються під час формування відповідей.
  - **Помилка обробки** — обробка перервана через збій (наприклад,
    пошкоджений файл або недоступність сервісу векторизації); документ MUST
    не використовуватися для відповідей, а причина помилки MUST бути
    доступною оператору.
  - **Дублікат** — хеш файлу збігається з уже обробленим документом; новий
    файл не обробляється повторно і посилається на результат наявного
    документа (див. FR-002–FR-003).
- **FR-008**: Система MUST надавати API-ендпоінт для надсилання текстового
  питання і отримання відповіді, сформованої на основі релевантних фрагментів
  бази знань.
- **FR-009**: Система MUST повертати відповідь, що явно вказує на відсутність
  релевантної інформації, коли жоден проіндексований фрагмент недостатньо
  релевантний до питання, замість вигаданої відповіді.
- **FR-009d**: Відповідь на питання MUST включати перелік документів-джерел
  (щонайменше назву кожного документа), фрагменти яких було використано для
  формування цієї відповіді; якщо релевантної інформації не знайдено
  (FR-009), перелік джерел MUST бути порожнім.
- **FR-009c**: Якщо зовнішній сервіс мовної моделі (LLM) повертає помилку або
  тимчасово недоступний під час формування відповіді, система MUST виконати
  рівно одну автоматичну повторну спробу; якщо повторна спроба також
  завершується помилкою, система MUST повернути клієнту чітку помилку (без
  подальших автоматичних повторів).
- **FR-009a**: Система MUST визначати мову, якою поставлено питання, і
  формувати відповідь тією самою мовою, якщо ця мова входить до
  налаштованого переліку підтримуваних мов (список підтримуваних мов MUST
  бути змінюваним через конфігурацію, без зміни коду).
- **FR-009b**: Якщо мова питання не входить до переліку підтримуваних мов,
  система MUST відповідати мовою за замовчуванням із того самого переліку
  (перший елемент конфігурації), а не мовою питання.
- **FR-010**: Система MUST записувати кожну пару «питання-відповідь» у
  журнал (сховище логів) разом з ідентифікатором сесії розмови та часовою
  міткою.
- **FR-010b**: Система MUST записувати в базу даних обсяг використаних
  токенів (вхідних і вихідних, або еквівалентну метрику вартості запиту) для
  кожного звернення до LLM, пов'язаний з відповідним записом журналу
  питання-відповідь. Ця інформація MUST не передаватися клієнту через API на
  цьому етапі — рішення про її подальше використання (звіти, ліміти
  вартості тощо) буде ухвалено окремо пізніше.
- **FR-010c**: Клієнт MUST мати можливість надіслати оцінку («корисно» /
  «некорисно») для конкретної відповіді за ідентифікатором відповідного
  запису журналу, за бажанням — разом із коротким текстовим коментарем.
  Повторна оцінка того самого запису MUST замінювати попередню, а не
  створювати дублікат.
- **FR-010a**: Оскільки API без стану і не використовує технічні HTTP/веб-сесії,
  сесія розмови MUST реалізовуватися як власний запис у базі даних із власним
  унікальним ідентифікатором, який система повертає клієнту у відповіді і
  який клієнт передає в наступних запитах для продовження тієї самої розмови.
- **FR-011**: Система MUST підтримувати сесію розмови: коли клієнт передає
  ідентифікатор існуючої сесії, попередні питання й відповіді цієї сесії
  MUST враховуватися при формуванні нової відповіді.
- **FR-011a**: Якщо клієнт передає ідентифікатор сесії, якого не існує
  (вигаданий, вже завершений через тайм-аут або видалений), система MUST
  автоматично створити нову сесію розмови з новим ідентифікатором і
  обробити питання без попереднього контексту, повернувши клієнту новий
  ідентифікатор сесії у відповіді.
- **FR-012**: Система MUST дозволяти клієнту розпочати нову сесію розмови без
  попереднього контексту (система створює новий запис сесії в базі даних і
  повертає його ідентифікатор).
- **FR-012a**: Система MUST автоматично завершувати сесію розмови (втрачати
  контекст) після налаштованого періоду неактивності; типове значення —
  1 година, значення MUST бути змінюваним через конфігурацію, а конфігурація
  зі значенням "необмежено" (null) MUST вимикати автозавершення (сесія живе
  безстроково, доки не буде завершена явно).
- **FR-013**: Доступ до API на цьому етапі MUST не вимагати повної системи
  користувачів/авторизації (це заплановано на майбутній етап), але доступ
  MUST бути обмежений технічним ключем/токеном доступу для запобігання
  неконтрольованому публічному використанню.
- **FR-013a**: Система MUST застосовувати базове обмеження частоти запитів
  (rate limiting) на технічний токен доступу (кількість запитів за проміжок
  часу, значення налаштовується через конфігурацію), щоб запобігти
  неконтрольованим витратам на зовнішній LLM API.
- **FR-013b**: Якщо клієнт перевищує ліміт частоти запитів (FR-013a), система
  MUST відхиляти запит з чіткою помилкою, що вказує на перевищення ліміту, і
  часом, через який можна повторити спробу.
- **FR-014**: Архітектура доступу до функцій завантаження та запитів MUST
  бути побудована так, щоб у майбутньому їх могли викликати різні канали
  (наприклад, Telegram-бот або вебсайт) без переробки основної логіки.
- **FR-015**: Система MUST надавати веб-сторінку зі списком усіх завантажених
  документів, що показує назву, статус обробки та дату завантаження кожного.
- **FR-016**: Веб-сторінка MUST надавати форму завантаження нового файлу
  документа, що використовує ту саму логіку обробки, що й API-завантаження
  (FR-001–FR-007).
- **FR-017**: Веб-сторінка MUST дозволяти видалити обраний документ, після
  підтвердження дії оператором. Видалення MUST виконуватися негайно навіть
  якщо фрагменти цього документа саме в цей момент використовуються для
  формування відповіді на активний запит (можливий рідкісний випадок, коли
  активний запит завершує формування відповіді зі "старими" фрагментами,
  отриманими до видалення).
- **FR-017a**: Видалення документа MUST бути м'яким (soft delete): документ і
  його фрагменти/векторні представлення позначаються як видалені й
  виключаються з подальшого використання, але не стираються фізично одразу
  — це дає змогу відновити документ у разі помилкового видалення. Остаточне
  (фізичне) видалення даних — рішення, яке буде ухвалено окремо пізніше.
- **FR-018**: Видалений (позначений як видалений) документ MUST негайно
  припиняти враховуватися під час формування нових відповідей на питання і
  MUST не відображатися в списку документів на веб-сторінці (FR-015).
- **FR-018a**: Спроба видалити документ, якого вже не існує в системі, MUST
  повертати чітку помилку («документ не знайдено») без збою сторінки чи
  API-відповіді.
- **FR-019**: Веб-сторінка керування документами на цьому етапі MUST бути
  доступною без входу в систему (авторизація для неї не реалізується на
  цьому етапі; це прийнятий тимчасовий ризик до впровадження повної системи
  користувачів).

### Key Entities

- **Document (Документ)**: завантажений файл бази знань; ключові атрибути —
  оригінальна назва, хеш вмісту, статус обробки (очікує обробки / обробляється
  / оброблено / помилка обробки / дублікат — див. FR-007), дата завантаження,
  ознака м'якого видалення (видалено/не видалено — див. FR-017a).
- **Chunk (Фрагмент)**: частина документа після розбиття, з якої створено
  векторне представлення; пов'язаний з батьківським документом і має позицію
  в межах документа.
- **Conversation Session (Сесія розмови)**: умовна (логічна) сутність, а не
  технічна HTTP-сесія — оскільки API без стану, це власний запис у базі
  даних, що штучно групує обмін повідомленнями в один діалог. Містить власний
  унікальний ідентифікатор (генерується системою при першому питанні й
  повертається клієнту для використання в наступних запитах), час
  створення, час останньої активності та впорядкований список повідомлень
  (питання-відповідь) цієї розмови. Саме на цей запис (а не на будь-яку
  HTTP/веб-сесію) посилаються всі записи журналу питання-відповідь.
- **Query Log (Журнал запитів)**: запис одного обміну питання-відповідь;
  містить текст питання, текст відповіді, посилання на сесію розмови,
  часову мітку, посилання на документи-джерела/фрагменти, використані для
  відповіді (див. FR-009d), та обсяг використаних токенів LLM для цього
  звернення (внутрішня метрика, не передається клієнту — див. FR-010b).
- **Answer Feedback (Оцінка відповіді)**: оцінка користувача щодо конкретного
  запису журналу питання-відповідь; містить значення оцінки («корисно» /
  «некорисно»), необов'язковий текстовий коментар та посилання на відповідний
  запис журналу. Кожен запис журналу MUST мати не більше однієї актуальної
  оцінки (повторна оцінка замінює попередню — див. FR-010c).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Оператор може завантажити типовий документ (PDF, до 20 сторінок)
  і отримати статус «готовий до використання» без ручного втручання.
- **SC-002**: Питання про факт, присутній у завантаженому документі, отримує
  фактично коректну відповідь щонайменше у 90% тестових випадків.
- **SC-003**: Повторне завантаження вже обробленого документа (без змін
  вмісту) не запускає повторну обробку і завершується миттєво (розпізнається
  як дублікат).
- **SC-004**: У межах однієї сесії розмови друге питання, що посилається на
  контекст першого, отримує відповідь, яка коректно враховує цей контекст,
  щонайменше у 90% тестових випадків.
- **SC-005**: Кожен оброблений запит питання-відповідь має відповідний запис
  у журналі, доступний для перегляду без відтворення запиту.
- **SC-006**: Оператор може завантажити та видалити документ через
  веб-сторінку без звернення до розробника чи прямих викликів API.
- **SC-007**: Якщо питання поставлене однією з підтримуваних мов, відповідь
  надається тією самою мовою щонайменше у 95% тестових випадків.
- **SC-008**: Система коректно обробляє базу знань обсягом до ~1000
  документів і одночасну роботу 5-10 користувачів без відмов чи суттєвого
  погіршення часу відповіді.
- **SC-009**: Кожна відповідь, яка спирається на базу знань, супроводжується
  переліком документів-джерел, що дає змогу перевірити її достовірність без
  звернення до розробника.
- **SC-010**: Клієнт може залишити оцінку якості для будь-якої відповіді
  протягом кількох секунд, без додаткової автентифікації понад ту, що вже
  використовується для доступу до API.

## Assumptions

- Комунікація на цьому етапі відбувається виключно через API (тестовий
  режим); Telegram-бот та вебінтеграція, а також повноцінна система
  користувачів/авторизації — це наступні окремі етапи, не входять у обсяг
  цієї специфікації.
- Основний формат документів для MVP — PDF (включно зі сканованими /
  переважно графічними сторінками, що вимагають розпізнавання зображень).
  Інші формати документів можуть додаватись пізніше.
- Вибір конкретного постачальника мовної моделі (LLM) та моделі
  розпізнавання зображень — це технічне рішення, яке буде визначено на етапі
  планування (`/speckit-plan`) на основі співвідношення якості, вартості та
  сумісності з Laravel-екосистемою; ця специфікація не фіксує конкретного
  постачальника.
- Обмеження доступу до API на цьому етапі реалізується найпростішим
  прийнятним способом (наприклад, статичний технічний токен), оскільки повна
  система користувачів запланована окремо.
- Тривалість зберігання логів питання-відповідь та історії сесій відповідає
  стандартній практиці зберігання операційних даних застосунку і не має
  спеціальних обмежень на цьому етапі.
- Веб-сторінка керування документами (завантаження/перегляд/видалення)
  розгортається без входу в систему й вважається доступною лише в
  довіреному/внутрішньому оточенні на цьому етапі; публічний доступ до неї
  без авторизації не передбачається.
- Конкретний перелік підтримуваних мов відповіді та мова за замовчуванням
  визначаються конфігурацією застосунку (не фіксуються цією специфікацією);
  очікується, що щонайменше українська та англійська входять до типового
  переліку.
