# Phase 0 Research: Агентний бот з пошуком в інтернеті та локалізованими промптами

## 1. Механізм пошуку в інтернеті

**Decision**: Використати вбудований інструмент `web_search` OpenAI через
Responses API (`OpenAI\Resources\Responses::create()`), який уже доступний у
встановленому пакеті `openai-php/laravel` (наявна залежність, без потреби
додавати нову) — з обмеженням на дозволені домени через параметр `filters.
allowed_domains` цього інструмента, що прямо відповідає FR-008a/FR-008b.

**Rationale**: OpenAI Responses API нативно підтримує вбудований веб-пошук
із сервер-side оркеструванням (модель сама вирішує, коли звернутися до
пошуку, і отримує результати з цитуванням URL в `annotations`) і
підтримує фільтрацію за дозволеними доменами "з коробки". Це усуває
потребу інтегрувати окремого стороннього провайдера пошуку (SerpApi,
Tavily, Bing тощо) — відповідає Принципу III конституції (Simplicity):
жодної нової зовнішньої залежності, використовуємо вже наявний
OpenAI-клієнт і вже налаштовану модель (`config('rag.openai.chat_model')`).

**Alternatives considered**:
- Сторонній API пошуку (Tavily, SerpApi, Google Custom Search) — відхилено:
  додає нову зовнішню залежність, окремий API-ключ і рахунок, тоді як
  вбудований інструмент OpenAI закриває вимогу без цього.
- Самостійний скрейпінг результатів пошукових систем — відхилено: крихко,
  юридично сумнівно, і зайва складність порівняно з готовим API.

## 2. Архітектура "агента" (рішення про виклик RAG/пошуку, кроки роздумів)

**Decision**: Замінити поточний детермінований конвеєр
`AnswerGenerationService::answer()` (завжди: ембединг → векторний пошук →
один виклик LLM) на обмежений цикл виклику інструментів (tool-calling
loop) через Responses API:
- Інструмент `search_knowledge_base` — кастомна функція, що обгортає вже
  наявні `EmbeddingService` + `VectorSearchService`; модель викликає її,
  коли вважає це потрібним (FR-001, FR-005), а не завжди наперед.
- Вбудований інструмент `web_search` (див. п.1) — модель викликає його
  самостійно, коли БЗ недостатньо (FR-001, FR-002, FR-004).
- Цикл обмежується конфігурованою кількістю кроків
  (`config('rag.agent.max_tool_steps')`, FR-006): після досягнення ліміту
  цикл примусово завершується запитом на фінальну відповідь без подальших
  викликів інструментів, на основі вже зібраної інформації.

**Rationale**: Це саме той патерн "агент, що сам вирішує, коли лізти в
RAG/інтернет", який прямо запитав користувач. Перетворення `RAG-пошук` із
"завжди виконуваного кроку" на "інструмент, який модель викликає за
потреби" — мінімальна зміна архітектури, що досягає мети: перевикористовує
`EmbeddingService`/`VectorSearchService` без змін їхньої внутрішньої
логіки, лише змінює точку виклику.

**Alternatives considered**:
- Ручна dual-LLM оркестрація (окремий "router"-виклик LLM, який спершу
  вирішує "RAG чи інтернет", потім другий виклик формує відповідь) —
  відхилено: складніше й повільніше (мінімум два послідовні виклики LLM
  замість вбудованого function-calling циклу в межах однієї розмови), а
  функціонально еквівалентне вбудованому tool-calling.
- Бібліотека агентних оркестраторів (LangChain-подібна для PHP) — у
  проєкті вже є `theodo-group/llphant`, але його agent-абстракції
  додають шар непрозорості над прямим tool-calling OpenAI без явної
  переваги для цього конкретного, відносно простого сценарію (2
  інструменти, обмежена кількість кроків) — пряме використання
  `openai-php` залишає код прозорішим і легшим для дотримання Принципу
  III.

## 3. Позначення джерел відповіді (документ vs. інтернет)

**Decision**: Розширити внутрішню (не БД) форму "джерела" з жорсткого
`Collection<DocumentChunk>` на масив нормалізованих записів із полем
`type` (`document` або `web`), що формується всередині
`AnswerGenerationService` одразу після завершення циклу інструментів —
для `document` включає `document_id`/`page_number`/`relevance` (як і
зараз), для `web` — `url`/`title` з `annotations` відповіді Responses API.

**Rationale**: FR-003 вимагає розрізняти джерела-документи й
джерела-інтернет у відповіді користувачу; найпростіший спосіб — привести
обидва типи до одного нормалізованого формату одразу в сервісі, що й так
має повний контекст виклику інструментів, замість передавання окремих
типізованих колекцій через увесь ланцюжок викликів.

**Alternatives considered**: окремі паралельні поля
`documentSources`/`webSources` через увесь стек (`AnswerGenerationService`
→ `QuestionAnsweringService` → API-контракт) — відхилено: подвоює логіку
на кожному рівні заради різниці, яку зручніше нести як одне поле `type`
всередині єдиного масиву.

## 4. Зберігання джерел у журналі (QueryLog)

**Decision**: `query_logs.source_document_ids` (JSON, уже існує) зберігає
масив нормалізованих джерел із п.3 без зміни схеми БД — кожен елемент
додатково отримує `type`; для існуючих записів (до цієї фічі) відсутність
`type` трактується як `document` (зворотна сумісність при читанні).

**Rationale**: Поле вже `json`/`array`-каст, довільної форми; додавання
нового ключа в елементи масиву — розширення без потреби в міграції
(Принцип V: сумісна зміна, не breaking).

**Alternatives considered**: нова таблиця `query_log_sources` — відхилено
як передчасну нормалізацію для даних, які й так завжди читаються разом із
записом журналу одним запитом.

## 5. Локалізація промптів через `__()`

**Decision**: Створити `resources/lang/en/bot.php`, що повертає масив
текстів інструкцій (системний промпт, визначення спеціалізації бота,
інструкція медичного застереження, інструкція переформулювання питання
для пошуку). Сервіси (`AnswerGenerationService`, `QueryRewriter`)
отримують ці тексти через `__('bot.system_prompt', [...])` замість
хардкоджених рядків у коді; мова добирається автоматично з
`config('app.locale')` (уже `env('APP_LOCALE', 'en')` — за замовчуванням
англійська, як і вимагалося).

**Rationale**: Пряма реалізація FR-009–FR-012 стандартним механізмом
Laravel (`__()` + `resources/lang/{locale}/...`) — жодної кастомної
інфраструктури локалізації не потрібно, повністю вбудовано у фреймворк
(Принцип III). Параметризовані частини промпту (мова відповіді,
контекст БЗ, перелік дозволених доменів) передаються через стандартний
механізм заміни плейсхолдерів `__()` (`:placeholder`).

**Alternatives considered**:
- Зберігання промптів у БД (редаговані через адмінку) — відхилено як
  надлишкове для поточного обсягу (одна мова, немає вимоги редагування
  без деплою) — YAGNI.
- JSON-файли локалізації (`lang/en.json`) — відхилено: для довгих
  багаторядкових інструкцій PHP-масив (`lang/en/bot.php`) зручніший і
  є стандартним підходом Laravel для структурованих груп перекладів.

## 6. Мовна відповідь користувачу (FR-012) vs. мова системних інструкцій (FR-010)

**Decision**: Без змін до `LanguageDetectionService` і логіки вибору мови
відповіді користувачу (`AnswerGenerationService` і далі каже LLM
"Answer in the language with code {detected}"). Ця інструкція сама
береться з `bot.php` (FR-009) параметризованою кодом мови користувача —
але вибір ЯКОЮ мовою написаний текст самої інструкції (наразі англійська)
незалежний від цього параметра, як зафіксовано в Clarifications.

**Rationale**: Просто підтверджує, що дві "мови" (мова системи для тексту
інструкцій і мова відповіді користувачу) технічно ніколи не конфліктують
— перша визначає, яким файлом `lang/{locale}/bot.php` користуємось, друга
— лише значення одного плейсхолдера всередині тексту цього файлу.

## 7. Обмеження кількості кроків агента (FR-006)

**Decision**: `config('rag.agent.max_tool_steps')`, за замовчуванням 4
(`env('RAG_AGENT_MAX_STEPS', 4)`) — досить для типового сценарію
"1× knowledge_base + 1× web_search + повторний виклик БЗ за потреби +
фінальна відповідь", без надмірного подовження часу відповіді.

**Rationale**: Конкретне число — технічний запобіжник (Assumptions
spec.md), не бізнес-вимога; 4 покриває User Story 2 (обидва джерела в
одній відповіді) з запасом на один повторний виклик, лишаючись у межах
прийнятного часу синхронного HTTP-запиту (SC-003).

**Alternatives considered**: ліміт за часом (секунди) замість кількості
кроків — відхилено як складніший у реалізації (потребує переривання
запиту, що вже в польоті) порівняно з простим лічильником ітерацій циклу.
