# Research: Telegram-бот + авторизація та ролі

**Feature**: `004-telegram-bot-auth-roles` | **Date**: 2026-10-19

Контекст проєкту, релевантний для рішень нижче:
- Існуюча Filament-панель (`app/Filament/Resources/DocumentResource`) **не має авторизації взагалі** — це свідомий тимчасовий ризик, задокументований у фічі 001 (`AdminPanelProvider`, коментар `FR-019`). Ця фіча додає авторизацію до вже існуючої панелі, а не створює нову.
- Єдиний Laravel auth guard — `web` (session-based), `SESSION_LIFETIME=120` (2 години) наразі ніким фактично не використовується (нема жодного залогованого флоу).
- Існує `QuestionAnsweringService` з коментарем, що передбачає "майбутній Telegram-бот" як ще один канал того самого RAG/агентного пайплайну — інтеграція має його просто повторно використати.
- `docs/new_scope_auth_telegram.md` вже зафіксував вибір `spatie/laravel-permission` для ролей.

## Рішення

### 1. Бібліотека для Telegram Bot API
**Decision**: `irazasyed/telegram-bot-sdk` (webhook-режим).
**Rationale**: типізовані методи (`sendMessage`, `editMessageText`, `answerCallbackQuery`, `sendDocument`), готовий парсинг вхідного webhook-апдейту (`Message`, `CallbackQuery`, `Contact`) — зmenшує обсяг власного коду порівняно з ручними HTTP-викликами. Активно підтримується, сумісний з Laravel 13.
**Alternatives considered**: `defstudio/telegraph` — більш "опінійований" (job-based відправка, власні моделі Chat/Bot) і важчий, ніж потрібно для одного бота з одним ботом/одним чатом модерації — відхилено за Принципом III (Simplicity). Власні HTTP-запити (`Http::post` до `api.telegram.org`) — довелося б вручну описувати типи апдейтів/клавіатур — більше кастомного коду, ніж тонкий SDK, тому відхилено.

### 2. Webhook vs long polling
**Decision**: Webhook (`POST /telegram/webhook/{secret}`), встановлюється artisan-командою.
**Rationale**: Відповідає рішенню, вже зафіксованому в `docs/new_scope_auth_telegram.md` (задача 5 "Регистрация бота, настройка webhook"); для production-деплою (web-сервер, а не постійний воркер) webhook природніший за long polling.
**Alternatives considered**: Long polling — вимагає окремого довготривалого процесу/воркера; не підходить для звичайного web-деплою без додаткової інфраструктури.

### 3. Нормалізація номера телефону (E.164)
**Decision**: Пакет `propaganistas/laravel-phone` (обгортка над `giggsey/libphonenumber-for-php`).
**Rationale**: FR-017a вимагає надійної нормалізації довільних форматів вводу до E.164; це саме задача, яку бібліотека на основі Google libphonenumber вирішує коректно (коди країн, 0 на початку, пробіли). Власний regex — відхилено, бо ненадійний для міжнародних номерів (Принцип III: готове рішення пріоритетніше кастомного).
**Alternatives considered**: Ручний regex-парсинг — крихкий, не покриває всі країни/формати.

### 4. Ролі та права
**Decision**: `spatie/laravel-permission`, ролі `user`, `moderator`, `admin`, `super_admin`.
**Rationale**: Вже узгоджено в `docs/new_scope_auth_telegram.md`; стандарт де-факто для Laravel, не потребує власної таблиці ролей/прав.
**Alternatives considered**: Колонка `role` enum на `users` — простіше для 4 статичних ролей, але відхилено, бо дублювало б рішення, вже прийняте в попередньому ТЗ, і ускладнило б майбутнє розширення прав (Filament-політики очікують `hasRole()`).

### 5. Авторизація Filament-панелі (заміна відсутнього логіну)
**Decision**: Використати вбудований механізм Filament `->login(CustomLoginPage)` + `FilamentUser::canAccessPanel()` на моделі `User`, замінивши стандартну сторінку email+пароль на кастомну 2-кроkову сторінку (телефон → код).
**Rationale**: Панель уже існує й використовує `AdminPanelProvider`; Filament нативно підтримує кастомні auth-сторінки без відмови від усієй іншої інфраструктури панелі (мідлвари, сесії). Відповідає Принципу III — розширення існуючого механізму замість побудови паралельної системи логіну.
**Alternatives considered**: Окрема Livewire-сторінка поза Filament зі своїм роутом логіну і ручним `Auth::login()` — можливо, але довелося б повторно реалізовувати захист сесії/CSRF, які Filament вже надає; відхилено.

### 6. Тривалість веб-сесії (8 год) та миттєве анулювання при зміні ролі
**Decision**: Два окремі механізми:
  (a) Таймаут — глобальний `SESSION_LIFETIME` (Laravel, в .env) піднімається до `480` (8 годин). Це безпечно, бо жоден інший флоу застосунку сесію не використовує.
  (b) Миттєве анулювання — нова колонка `users.sessions_invalidated_at`; при зміні ролі/деактивації супер-адміном це поле оновлюється; мідлвар на кожен запит до панелі порівнює час логіну, збережений у сесії, з цим полем і робить `Auth::logout()`, якщо сесія "старіша" за останню інвалідацію.
**Rationale**: (a) покриває стандартний таймаут без кастомного коду; (b) потрібен окремо, бо жоден стандартний таймаут не реагує миттєво на зміну ролі в іншій вкладці/сесії — це вимога FR-023a, яку неможливо покрити лише `SESSION_LIFETIME`.
**Alternatives considered**: Власна таблиця сесій із explicit expiry (аналог Sanctum-токенів) — дає той самий результат складнішим шляхом; відхилено, бо Laravel-сесія вже існує і потребує лише однієї додаткової перевірки.

### 7. Зберігання одноразового коду (OTP)
**Decision**: Власна таблиця `one_time_codes` (`user_id`, `code_hash`, `expires_at`, `attempts`, `consumed_at`), без зовнішнього 2FA-пакета.
**Rationale**: Логіка проста (генерація 6-значного коду, TTL 5 хв, максимум 3 спроби — вже зафіксовано в clarifications spec.md); зовнішній 2FA-пакет (наприклад, для TOTP/SMS) надлишковий, бо доставка коду відбувається через уже наявний канал (бот), не через SMS/email-провайдера.
**Alternatives considered**: `pragmarx/google2fa` чи подібні TOTP-пакети — не підходять, бо тут код одноразовий і генерується сервером, а не TOTP-алгоритмом на стороні клієнта.

### 8. Обробка натискання кнопок у груповому чаті модерації (callback_query)
**Decision**: При вхідному `callback_query` шукати користувача за `from->id` (Telegram user id) серед `users.chat_id`, перевіряти роль (`hasAnyRole(['moderator','admin','super_admin'])`); якщо ролі нема — `answerCallbackQuery` з текстом-тостом без зміни стану; якщо роль є — атомарно (через `DB::transaction` + перевірку поточного статусу заявки) обробити апрув/відхилення, щоб уникнути гонки двох одночасних натискань.
**Rationale**: Відповідає FR-004b/FR-006 (перевірка ролі, ігнорування повторного натискання) і найпростіший спосіб ідентифікації клікера — вже наявний `chat_id`, який бот зберігає під час онбордингу.
**Alternatives considered**: Окрема таблиця "учасників чату модерації" — зайва, бо роль і так уже є ознакою користувача в системі; відхилено.

### 9. Щоденні нагадування про необроблені заявки
**Decision**: Artisan-команда `telegram:send-approval-reminders`, що запускається через `Schedule::command(...)->dailyAt(config('services.telegram.reminder_time'))` у `routes/console.php` — за тим самим наявним шаблоном, що й `rag:purge-deleted-documents`.
**Rationale**: У проєкті вже є точно такий паттерн планових задач; нова команда вписується без нових абстракцій.

### 10. Кеш AI-резюме документа
**Decision**: Нова таблиця `document_summaries` (`document_id`, `locale`, `summary`, `created_at`) з унікальним індексом `(document_id, locale)`, а не JSON-колонка на `documents`.
**Rationale**: Окрема таблиця дозволяє не чіпати існуючу `documents`-таблицю (міграції фічі 001/002) і природно підтримує множинні мови через рядки замість вкладеного JSON; простіше для індексації й вибірки.
**Alternatives considered**: JSON-колонка `summaries` на `documents` — технічно можливо (так і було написано як варіант у вихідному ТЗ), але ускладнює унікальність/індексацію по мові; відхилено.

### 11. Інтеграція вільного чату з AI
**Decision**: Повторно використати існуючий `QuestionAnsweringService` (та агентний режим, якщо включений) як є — Telegram-канал викликає той самий сервіс, що й API/публічний чат, передаючи `chat_id` як ідентифікатор `ConversationSession` (той самий механізм 1-годинного тайм-аута, вже реалізований у фічі 001, `config/rag.php: session_timeout_minutes`).
**Rationale**: Саме так і було закладено в коді (`QuestionAnsweringService.php`, коментар про "майбутній Telegram-бот"); нуль нового коду для самого RAG-пайплайну, лише новий "канал" прив'язки сесії.

### 12. Пагінація списку документів у боті
**Decision**: Номер сторінки передається прямо в `callback_data` інлайн-кнопок ("Далі"/"Назад", напр. `docs_page:2`), без збереження стану пагінації на сервері.
**Rationale**: Проста, типова для Telegram-ботів схема; не вимагає нової таблиці чи сесії для UI-стану.

### 13. Обмеження частоти запитів одноразового коду (rate limit)
**Decision**: `Illuminate\Cache\RateLimiter` (вбудований Laravel) з ключем за нормалізованим номером телефону, ліміт 3 запити/хвилину (FR-019b, уточнено в clarify-сесії від 2026-10-19).
**Rationale**: Готовий механізм Laravel, не потребує нової таблиці чи зовнішнього пакета; достатньо для захисту від підбору номера й спаму повідомленнями від бота на масштабі цього проєкту.
**Alternatives considered**: Власна таблиця лічильників спроб — зайва складність, коли `RateLimiter` вирішує це в одну стрічку коду.

### 14. Інвалідація попереднього одноразового коду при запиті нового
**Decision**: При генерації нового `OneTimeCode` для користувача всі попередні незавершені коди цього користувача одразу позначаються як інвалідовані (`invalidated_at`), FR-019a.
**Rationale**: Унеможливлює ситуацію, коли дійсні кілька кодів одночасно (плутанина, більша поверхня для підбору); узгоджено з clarify-сесією від 2026-10-19.

### 15. Дублікат номера телефону при онбордингу
**Decision**: Якщо номер з Telegram-контакту вже закріплений за іншим `telegram_chat_id`, онбординг відхиляється повідомленням "номер вже зареєстровано" (FR-003a); новий `User`-запис не створюється.
**Rationale**: Найпростіший і найбезпечніший дефолт — автоматична перепідв'язка номера до нового Telegram-акаунту без верифікації була б вектором для захоплення чужого доступу.
